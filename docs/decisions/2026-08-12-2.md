## 1. I deleted a safety warning from CLAUDE.md because it had come true. Confirm?

**What happened.** CLAUDE.md told every batch: *"staging is EMPTY, so there is still nothing to
rehearse against… every migration is still UNREHEARSED against production… defer destructive ones."*

That stopped being true on 11 August, when we built the staging database, three seed files and a
seven-step migration procedure. The warning had sat there for four days — and the next four things
in the queue are all database migrations, so every one of them would have read it first and been
told to be more careful than it needs to be, on the basis of something false.

**Why I acted rather than asking first.** The warning contained its own expiry date. It said the
safeguard becomes real *"when the queue's staging item RUNS"* — and it ran. So honouring that
sentence is what I did, rather than overriding you.

**What I changed it to.** It now points at `docs/STAGING.md` for the procedure, and I kept the half
of the warning that is still true and wrote it out more plainly: staging uses invented data, so it
proves a migration RUNS and never that it gives the right answer for your café; and neither database
has more than one user, so it cannot prove a second café's data is properly walled off.

**What protection changed, stated plainly because this is the bit worth your eye.** The old text
said "defer destructive ones". That instruction is gone from that bullet — but the rule itself is
untouched and still sits four lines below it: *anything that DELETES or REWRITES data is still
Max's.* So nothing destructive happens without you either way. What I removed was a second, weaker
copy of a rule you already have.

- **Yes** — leave it as I've written it.
- **No, put the caution back** — and migrations stay slower until you say otherwise.

**My recommendation: yes.** A warning that is factually wrong doesn't make anything safer, it just
gets trusted about the wrong things. The real protection is the destructive-work rule, which hasn't
moved.

**What would change it:** if you'd rather every migration still stop and say "this is unrehearsed"
out loud even though it isn't. That's a taste call about how much ceremony you want, and it's yours.

## 2. A new rule for CLAUDE.md: a CSS mistake can silently delete the rest of the file

**Where this came from.** It cost the last batch a full diagnose cycle. Someone typed comment text
without its opening `/*`. The browser did what the rules say it must — threw away the broken rule
*and every rule after it* — so a chunk of the stylesheet was simply absent. The page still loaded,
all 986 tests passed, every check was green, and the only symptom was one measurement coming back
wrong.

**Why it wants to be a rule.** There's no build step here and nothing reads the stylesheet except
the browser, so this class of mistake has no natural way to surface. A test was written for it
(`tests/css-syntax.test.js`) and it catches it in 40 milliseconds. The rule is what tells the next
person why that test exists and not to delete it as trivial.

**Options**
- **A. Add it to CLAUDE.md as a Tier 1 trap.** (Recommended.) Costs about six lines in the file.
- **B. Leave it in the handover only.** Free, and it disappears — the audit found *four* separate
  cases of something written in a handover and nowhere else, then quietly forgotten. This would be
  the fifth.
- **C. Leave it to the test alone.** The test keeps working, but the first person to find it
  inconvenient deletes it, because nothing says why it matters.

**My recommendation: A.** It fits your own bar for that file exactly — a mistake that already
happened once, that a competent person would not predict, and that no amount of careful reading
catches.

**What would change it:** if you think CLAUDE.md is getting long enough that only bugs which cost
real money belong in it. This one cost an hour, not a menu.
