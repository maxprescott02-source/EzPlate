# UI/UX audit — 2 Sep 2026 (Phase 1, audit only)

Every screen rendered at 375, 390, 768, 1024, 1280, 1440 and 1920 px, in populated and
empty states, against the café's real data (the full catalogue, all plates and dishes,
the complete price history). 146 screen captures plus a modal, keyboard, scroll-bottom
and zero-results pass. **No code was changed in this phase.**

## Where the evidence lives — and why it is NOT in this repo

⚠️ **The capture set is deliberately not committed.** This repository is public, and the
populated screenshots show real plate costs, sell prices, food-cost percentages, supplier
names and a real phone number — exactly the class of business data CLAUDE.md records as
this repo's actual leak. A committed screenshot is world-readable forever.

- The full set (146 captures, sliced copies, modal shots, per-screen measurement JSON,
  and the harness that produced them) is preserved locally at
  `~/Documents/EzPlate-ui-audit-2026-09-02/`.
- It is **fully reproducible**: the harness boots the real app through the same Supabase
  shim the Playwright specs use, seeded from a read-only export. `node run.js` in that
  folder regenerates everything (`run.js` serves the repo with `python3 -m http.server`
  and uses the repo's own Playwright install).

## Setup

The app is online-only with sign-in mandatory, so production could not be pointed at
directly. Real data was exported read-only from Supabase and served through a boot shim
modelled on `tests/visual/_boot.js`, signed in as an owner. The empty state serves every
table empty; the signed-out and no-café gates were captured separately.

## Framework, styling, screens

- **Framework: none.** Hand-written static PWA — `index.html`, one browser script
  (`js/app.js`), `css/style.css`, `sw.js`. No build step, no router.
- **Styling:** one stylesheet, already substantially tokenised — light/dark palette on
  `:root` / `html[data-theme="dark"]`, a `--fs-*` type scale, a 4px `--sp-*` spacing
  scale, radius and motion tokens, plus an alias layer for legacy names. The debt is
  ~95 off-scale font-size literals (40× `13px`, 27× `12.5px`, 17× `11.5px`, 11× `13.5px`)
  and nine distinct breakpoint values (380, 520, 560, 639, 640, 700, 767, 768, 1023, 1024).
- **Screens** (tab panes toggled by `showTab`): Dashboard · Menu (`analysis`) · Plates
  library (`builder`) · Ingredients (`pantry`) · Products (`ingredients`) · Invoices ·
  Settings · Account · More (mobile hub, absorbs the last four below 1024) — plus the
  full-page plate builder (`#builderPage`), the signed-out and no-café gates, and ~20
  modal overlays. Navigation renders three ways: bottom tab bar <768, icon rail
  768–1023, full sidebar ≥1024.

## The verdict

Phones (375–390) and desktop (1024+) are in good shape — consistent header grid, no
overflow, big inputs, real empty states. **The 768–1023 tablet band is broken on all
three data tables**: the desktop column templates apply from `min-width:768` but their
fixed tracks only fit at ≥1024, so the Menu screen shows two-letter dish names, the
Ingredients screen grows 200px-tall rows, and the Products screen silently clips its
"Last change" column offscreen. One CSS commit per table fixes the worst of this audit.

## What was checked and came back clean

- No horizontal page scroll in any of the 146 runs — every screen, width and state
- Every input ≥16px font — iOS will never zoom-on-focus
- Focus rings on every element sampled (26 `:focus-visible` rules, global + per-component)
- Tab order is logical: nav → sidebar group → content
- Safe-area insets handled (20 usages, `viewport-fit=cover`)
- Bottom stack behaves: content clears banner + tab bar at page bottom (the v186 work holds)
- Loading splash, offline toast, signed-out gate, no-café gate all present and legible
- Empty states are illustrated with real guidance; zero-search-results states exist
- Sticky cost panel and dropdown anchoring in the builder behave at every width
  (the v189 containing-block fix holds)
- Dark theme is fully tokenised (token review; screen-by-screen pass pending, see limits)

## Limits of this audit

Rendered in headless Chromium on macOS, light theme. Not exercised: real iOS Safari
(`docs/PHONE.md` covers device checks), the dark theme screen-by-screen (a re-run of the
matrix with `data-theme="dark"` is cheap if wanted), the invoice *review* table (needs a
parsed invoice; its renderer has its own regression suite), and print stylesheets.
Contrast figures are computed from flattened backgrounds and worst-case sampled, not
exhaustive.

## Phase 2 plan (constraints: no functional change, no new dependencies, CSS/markup only, one defect class per commit)

1. **Token layer only** — fold off-scale literals onto the existing `--fs-*`/`--sp-*`
   scales and rationalise breakpoints, value-preserving, zero visual change. (The scales
   already exist; this is completion, not creation.)
2. **Shared layout primitive** — `.scr-head` already locks title + action; extend it to
   lock the search/filter row too, and bring the Menu screen onto it (R4, R7).
3. **One commit per defect class, highest severity first**: R1 → R2 → R3 (the tablet
   band), then R5/R6 (touch targets), then the cosmetic set. Every commit: suite +
   smoke + Playwright green, before/after shots at 390 and 1440, diff confined to
   `css/style.css`/`index.html` or the exception named.

R8 and R12 need a yes for one-line JS changes; everything else is CSS/markup within the
constraints. Done means every row above is marked fixed, deferred or wontfix with a reason.
